description: Ограниченный доступ для пользователя с закончившейся подпиской — только Telegram, оплата и страница подписки, с малой скоростью и квотой. Всё на ноде, без правил в клиенте.

Когда подписка заканчивается, пользователя можно не отключать полностью, а оставить ему узкий доступ: Telegram, страницы оплаты и страницу подписки, с маленькой скоростью и квотой. Ограничение работает на ноде — клиентский конфиг не меняется и обойти его нельзя.

Отдельной функции для этого нет: режим собирается из [лимитов пользователей](/Citrus/start/user-limits/), правила `IN-USER` и `PUT /rules`.

## Почему не `expire-at`

`expire-at` проверяется в туннеле после правил и отклоняет **любое** соединение пользователя, в том числе к разрешённым адресам. Поэтому пользователю в «льготном» режиме `expire-at` не ставят: панель сама решает, когда подписка закончилась, и переводит пользователя в этот режим — меняет ему лимит и добавляет в список правил.

## Конфиг

```yaml
rule-providers:
  grace-allow:            # что доступно в льготном режиме
    type: inline
    behavior: classical
    payload:
      # Telegram
      - DOMAIN-SUFFIX,telegram.org
      - DOMAIN-SUFFIX,t.me
      - DOMAIN-SUFFIX,telegram.me
      - DOMAIN-SUFFIX,telegra.ph
      - DOMAIN-SUFFIX,telesco.pe
      - DOMAIN-SUFFIX,cdn-telegram.org
      - IP-CIDR,91.105.192.0/23
      - IP-CIDR,91.108.4.0/22
      - IP-CIDR,91.108.8.0/22
      - IP-CIDR,91.108.12.0/22
      - IP-CIDR,91.108.16.0/22
      - IP-CIDR,91.108.20.0/22
      - IP-CIDR,91.108.56.0/22
      - IP-CIDR,149.154.160.0/20
      - IP-CIDR,185.76.151.0/24
      - IP-CIDR6,2001:67c:4e8::/48
      - IP-CIDR6,2001:b28:f23c::/48
      - IP-CIDR6,2001:b28:f23d::/48
      - IP-CIDR6,2001:b28:f23f::/48
      - IP-CIDR6,2a0a:f280::/32
      # оплата и страница подписки
      - DOMAIN-SUFFIX,panel.example.com
      - DOMAIN-SUFFIX,pay.example.com
      # DNS клиента, если он резолвит через туннель
      - DST-PORT,53

user-limits:
  # льготный лимит: без expire-at
  - { inbound: vless-in, user: alice, speed-up: 64K, speed-down: 128K, quota: 200M }

rules:
  - AND,((IN-USER,alice/bob),(RULE-SET,grace-allow,no-resolve)),DIRECT
  - IN-USER,alice/bob,REJECT
  # ... остальные правила ноды
  - MATCH,DIRECT
```

- `IN-USER` принимает список имён через `/`; список проверяется за постоянное время, поэтому в нём могут быть тысячи пользователей.
- Первое правило пропускает пользователей из списка к разрешённым адресам, второе отклоняет всё остальное от них. Остальных пользователей эти правила не касаются.
- `no-resolve` не даёт ноде резолвить домен ради `IP-CIDR`: соединение к домену проверяется по доменным правилам, к IP — по `IP-CIDR`.
- Доменные правила срабатывают, когда клиент присылает домен (так делает большинство клиентов). Telegram сработает и по `IP-CIDR`. Если клиент присылает только IP, домен можно восстановить [сниффером](https://wiki.metacubex.one/config/sniff/) на ноде, но только с `override-destination: true`: без него правила проверяют домен из SNI, а соединение идёт на исходный IP, и пользователь в льготном режиме дойдёт до любого сервера, подставив в SNI `web.telegram.org`.
- `DST-PORT,53` нужен клиентам, которые отправляют DNS-запросы через туннель: без него они не узнают даже адрес Telegram. Через порт 53 пройдёт любой трафик — но только в пределах льготных скорости и квоты; если клиенты резолвят сами, строку можно убрать. Уже, чем порт целиком, — только известные резолверы: `AND,((DST-PORT,53),(IP-CIDR,1.1.1.1/32))` и так для каждого адреса, которым пользуются ваши клиенты.
- Имя в `IN-USER` — имя пользователя на любом входящем. Если одно имя есть на нескольких входящих, а ограничить нужно только один, добавьте в `AND` условие `IN-NAME,vless-in`.
- Лимит задаётся для пары «входящий» + «пользователь»: если пользователь подключается к нескольким входящим, задайте лимит на каждом.

## Перевод в льготный режим без перезапуска

Панель делает четыре запроса к `external-controller`:

```bash
API=http://127.0.0.1:9090; AUTH="Authorization: Bearer $SECRET"

# 1. льготный лимит; он заменяет прежний целиком, expire-at пропадает
curl -X PUT -H "$AUTH" "$API/limits/users?inbound=vless-in&user=alice" \
  -d '{"speed-up": "64K", "speed-down": "128K", "quota": "200M"}'

# 2. квота с нуля: PUT сохраняет трафик, потраченный за время подписки
curl -X POST -H "$AUTH" "$API/limits/users/reset-quota?inbound=vless-in&user=alice"

# 3. правила с пользователем в списке (весь список rules целиком)
curl -X PUT -H "$AUTH" "$API/rules" -d '{"rules": [
  "AND,((IN-USER,alice/bob),(RULE-SET,grace-allow,no-resolve)),DIRECT",
  "IN-USER,alice/bob,REJECT",
  "MATCH,DIRECT"]}'

# 4. закрыть открытые соединения пользователя
curl -X DELETE -H "$AUTH" "$API/connections?inbound=vless-in&user=alice"
```

- Новые правила действуют на новые соединения; уже открытые остаются как были. Шаг 4 закрывает их, клиент переподключается уже по новым правилам. Скорость и квота действуют и на открытые соединения сразу.
- Между шагами 1 и 2 пользователь, потративший больше льготной квоты, на мгновение упирается в неё; это безопасно.
- Когда пользователь оплатил, панель делает то же в обратную сторону: обычный лимит (`PUT /limits/users`, при необходимости `reset-quota`) и правила без него в списке. Закрывать соединения не нужно — новые и так пойдут по обычным правилам.
- Если пользователь исчерпал льготную квоту, его соединения закрываются и новые отклоняются — в том числе к Telegram, — пока квоту не сбросят или не увеличат.

## После перезагрузки конфига

`PUT /rules` и `PUT /limits/users` живут в памяти: перезагрузка конфига возвращает правила и лимиты из конфига. Поэтому панель пишет то же состояние и в конфиг ноды — список `IN-USER` в `rules` и льготные лимиты в `user-limits`, как в примере выше.

## Список в rule-provider

Вместо правки `rules` список можно держать в отдельном rule-provider — тогда `rules` не меняются вовсе:

```yaml
rule-providers:
  grace-users:
    type: http                 # или file
    url: https://panel.example.com/nodes/node-1/grace-users.txt
    behavior: classical
    format: text
    interval: 3600
  grace-allow: { ... }         # как выше

rules:
  - AND,((RULE-SET,grace-users),(RULE-SET,grace-allow,no-resolve)),DIRECT
  - RULE-SET,grace-users,REJECT
  - MATCH,DIRECT
```

Файл — строки `IN-USER,alice` (или одна строка `IN-USER,alice/bob/…`: она проверяется за постоянное время, а отдельные строки — по очереди). Пустой файл — никто не ограничен. После изменения списка панель вызывает `PUT /providers/rules/grace-users`, и нода сразу перечитывает его; шаг 3 выше заменяется этим вызовом, остальные шаги те же. Список переживает и перезагрузку конфига.
