description: Исходящий desync — это DIRECT-соединение, приспособленное к сетям с DPI-фильтрацией. Он меняет то, как отправляется первый TLS ClientHello, а не то, что получает сервер.
---

Исходящий `desync` приспосабливает прямые соединения к сетям с DPI-фильтрацией. Он подключается как `DIRECT` и до отправки преобразует первый TLS ClientHello соединения: делит его на несколько TLS-записей или TCP-записей, а на Windows может сначала отправить поддельный префикс с малым TTL. Сервер получает тот же handshake. Всё после ClientHello и соединения, которые начинаются не с него, проходят без изменений. Это не туннель, сервер ему не нужен. Преобразования берутся из библиотеки [desync](https://github.com/Nemu-x/desync).

```yaml
proxies:
  - name: desync-yt
    type: desync
    tlsrec: "1+s"            # позиции через запятую
    # split: "2"             # по желанию: отдельные TCP-записи
    # split-delay: 0         # пауза между ними в мс, 0–1000
    # fake: { ttl: 4, prefix: -1, timeout: 3000 } # только Windows
    # udp: { ttl: 4, repeats: 6, packets: 3 }     # только Windows

proxy-groups:
  - name: youtube
    type: fallback
    proxies: [desync-yt, vpn-node]   # сначала desync, узел прокси в резерве
    url: https://www.youtube.com/generate_204
    interval: 300

rules:
  - DOMAIN-SUFFIX,youtube.com,youtube
  - DOMAIN-SUFFIX,googlevideo.com,youtube
  - MATCH,DIRECT
```

## Параметры

| Ключ | Что задаёт |
| --- | --- |
| `tlsrec` | Где делить ClientHello на TLS-записи. `3` — байт 3 TLS-потока (считая от заголовка первой записи), `1+s` — один байт после начала имени сервера. |
| `split` | Где делить его на отдельные TCP-записи, в той же нотации. Как поток делится на TCP-сегменты, решает операционная система. |
| `split-delay` | Пауза между записями `split` в миллисекундах, 0–1000. Нужен `split`. |
| `fake` | Только Windows. Отправляет другой префикс с малым числом хопов (`ttl`), затем исходные байты для повторной передачи. `prefix` считается после деления на записи, отрицательный — от конца (по умолчанию `-1`); `timeout` ограничивает системную отправку в миллисекундах (по умолчанию 3000). Не сочетается со `split`. |
| `udp` | Только Windows. Перед каждой из первых `packets` (1–8, по умолчанию 3) датаграмм к адресату отправляет `repeats` (1–16, по умолчанию 6) датаграмм с малым TTL; исходные не меняются. Без `udp` UDP этого исходящего — обычный DIRECT. |
| `interface-name`, `routing-mark`, `ip-version` | Как у `direct`. |

Нужен хотя бы один из `tlsrec`, `split`, `fake` или `udp`. `tfo`, `mptcp` и `dialer-proxy` не принимаются: с TFO ClientHello ушёл бы вместе с SYN, до того как его можно разделить. `fake` и `udp` на Linux, macOS и Android — ошибка конфига, а не молчаливый DIRECT.

## Маршрутизация

Исходящий выбирается как любой другой: правила и группы ссылаются на него по имени, глобальный `DIRECT` не меняется. Проверки здоровья и URL-тесты исходящего проходят через преобразование, поэтому группа fallback или url-test переключится на узел прокси, когда маршрут через desync перестанет работать, и вернётся, когда он заработает. Имена он разрешает через `direct-nameserver`, как DIRECT, подключается к адресу, проверенному IP-правилом, и отклоняет собственное соединение, вернувшееся через листенер Citrus.

Значения TTL вроде 4 — примеры, а не значения, подходящие любой сети: поддельный пакет должен истечь после фильтрующего оборудования и до сервера. Поможет ли способ, зависит от сети; локальная проверка показывает только, что байты отправлены так, как настроено.

## API контроллера

`GET /proxies` показывает исходящий с `"type": "Desync"` и объектом `desync`: действующая стратегия `strategy` (`static` — заданные параметры), параметры `tcp` и, с `udp`, его параметры и счётчики исходных и поддельных датаграмм, ошибок и адресатов. Счётчики показывают, что датаграммы отправлены, а не что они помогли.
